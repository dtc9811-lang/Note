# 《百世飞升》正文执行

正文执行的目标是把已批准施工单写成可验收稿。施工单提供骨架与边界，不是逐句分镜；写手应主动完成场景调度、对话攻防、动作细节、气氛和局部转折，让人物像在现场做选择。

## 领取任务

1. 先调用 DevTrace `resolve_workspace(cwd="F:\\novel")` 与 `get_task_context`。
2. 用户明确要求执行某个 DevTrace Task 时，调用一次 `start_work(task_id, agent)`，严格执行返回的**一个** work item。不要自行领取下一项。
3. 用户直接给出工单或文件时，不要为了取得 item id 调用 `start_work`；按现有授权处理，并用 `record_progress(change)` 回写。
4. 若返回 `wait/done/stop`，停止写作，不绕过队列。

`start_work` 返回的 `story_ledger` 是已经验收、仍需后文记住的短期连续性；返工时还会包含本工单自己的待审卡。动笔前读完这些卡，不能把临时人物、线索或物件状态自动复原。

当前 work item 的标题、spec、inputs 和 output 高于 Task 的旧标题、旧 description 与历史分工表。若它们不一致，按当前 item 执行，并把陈旧元数据记为 `finding`；不要退回旧章号写作。

## 最小必读集

- `F:\novel\AGENTS.md`
- DevTrace work package、当前裁定与本章工单
- `写作资料/01_写作规则.md`
- `写作资料/02_设定总表.md` 中本章涉及的术语与人物段落
- 上一章已验收稿最后三十行；涉及物件、伤势或数字时再检索其首次出现与最近状态
- work package 点名的旧章或资料

续写阶段不需要通读无关旧稿。`归档/`、备份和未点名的 `待处理/` 不是依据。

## 动笔前先做事实表

在草稿外整理六项：

1. 必须出现的人、话、动作、物件和结果
2. 禁止出现的解释、专名、数字和提前揭露内容
3. 开场人物位置、伤势、修为、物件归属
4. 本章允许新增的长期事实、专名和剧情数字，以及明确留给写手的自由区
5. 每个角色知道什么、不知道什么
6. 章末必须留下的可见状态

事实表是自检材料，不得改写成正文里的解释句。

## 自由发挥边界

写手可以自由决定：

- 场景切入口、镜头顺序和转场方式
- 对话的具体措辞、试探与反击步骤
- 无名路人的即时反应与短暂介入
- 既有地点中普通、合理的声响、天气、器物和身体动作
- 只在本场生效并于本场闭合的小阻碍、误会、失败与应对
- 不改变力量结论的比喻、节奏和感官细节

判断标准是：后文是否必须记住它。若一个细节离开本场后无需登记，不改变人物能力、关系、物件、规则、地图和因果，它通常属于自由发挥，不必等工单授权，也不必逐项写入 DevTrace。

如果发现比施工单示例更自然的等效实现，可以直接采用：必须由同一人物作出选择，承担同等或更清楚的代价，抵达同一不可逆结果，不改变后续接口。交付时把这种等效实现列在“偏离”中即可，不必先停下来请示。

短期连续性可以由写手自行创造，但必须通过故事台账交接：只在一至五章内活动的本地人物、小冲突、线索、普通物件换手和局部关系变化，不必等规划者预先写进工单；一旦离开本场后仍须记住，就用 `story_register` 或 `story_handoff` 登记。

仍需要正式工单或 `decision` 裁定的，是新能力、新地点或机构、新势力、新法宝与关键物件、物件永久换手、修为伤势变化、日期距离钱数、关键人数和资源量、公开规则、人物长期关系与承诺、跨卷伏笔。

## 故事台账交接

- 天气、声响、普通器物、无名路人动作和本场闭合的小误会不登记。
- 新增具名短期人物、跨章小剧情、线索、普通物件或关系变化时，调用 `story_register`，绑定当前 `work_item_id`；临时卡最迟结清章不得超过首次出现后五章。
- 临时人物的 `details` 至少写 `desire`、`leverage`、`knowledge`、`exit_plan`；短剧情至少写触发、允许结果范围和退出方式。
- 使用已有卡时按 `story_lookup` 返回的 `version` 调用 `story_handoff(expected_version=...)`，报告当前状态、下一手和是否 `resolved/abandoned`。版本冲突时重新查表，不覆盖别人。
- 临时卡不能补隐藏修为、血脉、宗门背景或古老身份，不能改变工单锁定的选择者、代价、不可逆结果和后续接口。
- 需要跨五章或跨卷时停止把它当临时发挥，报告为待裁定；只有同项目 `decision` Event 建立后，验收者才能用 `story_review(promote)` 升级。

## 写作边界

- 第三人称限知贴赵升；只写他能看见、听见或有依据推断的内容。
- 工单给出的事实写成动作、物件、对话和后果。不要把“认功能不认人”“不是坏人”“没有威胁”等规划结论原句搬进旁白。
- 可以新增已用故事台账登记、五章内退出的具名短期人物；不得借临时人物新增势力、能力、机构隶属、历史年代或长期身份。未登记的跨章人物、地名、势力、法宝和剧情数字仍不得进入候选稿。
- 不把人物写得比工单更坏、更强、更懂或更愤怒。利益对手的道理必须由其行为和对话成立。
- 空间、时间、物品、人数、信息五项守恒。人物移动要交代；物件不能凭空换手；未在场者不能知道过程。
- 伤势与代价跨章延续，不能在下一章开头自动恢复。
- 修炼、战斗和硬规则场先核对数字与触发条件，再写感受；不靠形容词替代规则动作。
- 主动使用施工单保留的 20%—30% 场景自由度。自由发挥可以改变过程和读感，但不能偷改既定结果或制造需要后文解释的新事实。

## 完稿自检

1. 在 `F:\novel\百世飞升续写` 运行 `python 脚本/候选稿体检.py <候选稿> --min-chars <下限> --max-chars <上限> --scene-count-min <下限> --scene-count-max <上限> --scene-min <每场下限>`；只把工单要求逐字出现的原句和明确禁词作为 `--require`、`--forbid`，概念性要求由人工判断。
2. 交付时同时报告候选稿体检的“去空白字数”和 `文风体检.py` 的正文字数，不能混写。
3. 在同一目录运行 `python 脚本/文风体检.py <候选稿绝对路径>`。
4. 人工复核未登记专名、会形成剧情债的未授权数字和脚本无法判断的同义改写。“一步”“一声”“双手”等自然量词不因工单未列就机械删除。
5. 查询 `story_ledger`：本章使用或新增的跨章内容都已登记，已有卡已 `handoff` 或结清，没有到期仍悬空的卡。
6. 逐项核对事实表，尤其检查“离开以后才复位”“只有在某位置才触发”这类动作顺序。
7. 候选稿尚未并入 `分章/` 时，不运行或改写正式全本；只有晋升正文后才执行 `正文管理.py 全本/检查`。

字数不足时补冲突、选择、验证或交接动作；不要靠无效景物和重复解释凑字。删越线内容后重新实测，不能沿用修改前数字。

## 交付

通过 `start_work` 领取的 item，先完成故事卡登记/交接，再用 `submit_work`；检查返回的 `story_delta`，并保留 `item_id` 供验收。直接任务用 `record_progress(change)`；若直接任务也产生短期跨章连续性，可不绑定 item 登记，但必须在交付说明中列出卡片 id。

交付说明写清：实际发生、必留项、自由发挥、新增事实、偏离、去空白字数、各场长度、文风结果、章末状态、未决矛盾。不要声称未实际运行的检查已经通过。

遇到验收关口，提交后停止；不要自行规划或领取下一章。
