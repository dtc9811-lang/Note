# 《百世飞升》正文验收

验收要判断稿件是否完成施工单、是否违反既定事实、是否产生必须登记的新事实，以及下一章规划是否需要调整。审美偏好不能代替返工理由。

## 开工入口

1. 调用 DevTrace `resolve_workspace(cwd="F:\\novel")` 与相关 Task 的 `get_task_context`。
2. 读取目标章的 `change`、准确工单、候选正文、上一章已验收稿末尾，以及本章涉及的设定或裁定。
   同时读取 `submit_work` 返回的 `story_delta`；需要展开时用 `story_get`。没有 item id 的直接稿，用 `story_lookup` 核对相关卡片。
3. 不要以 reviewer 身份调用 `start_work` 来寻找 item id；这会误领下一张写作工单。
4. item id 已知时用 `review_work`；未知时用 `record_progress(test)`，不要猜 id。

## 四层验收顺序

### 1. 硬事实

先核对人名、人数、生死、修为、伤势、时间、地点、物件归属、角色信息来源、规则触发顺序。正文、较新 decision 与设定冲突时，按项目事实优先级裁定。

特别检查常见错误：

- 木牌、铁器、账册等材质或持有人被改写
- 活人、暗位、亮位、复位等规则动作次序不完整
- 未在场角色知道了过程
- 人物离开后又无交代出现
- 工单没给的地貌、机构隶属、能力、年代、钱数和尺寸进入正文
- 跨章具名临时人物、短剧情、线索或物件变化进入正文却没有故事卡，或卡片状态与正文不一致

这里检查的是会形成连续性债或改变世界事实的新增内容。普通天气、声响、既有场所中的日常器物、无名路人的现场动作和自然量词，不因工单没逐项列出就判错。

### 2. 工单兑现

逐项核对章节目标、必留、禁区、章末落点与开场/收尾状态。检查是否把“不许清单”或规划结论抄成旁白，是否解释开放伏笔，是否把利益对手写成纯坏人。

### 3. 结构与读感

核对不可逆事件和至少两类脉冲；检查是否连续三章仍在同地点、同冲突或只靠讨论记账。人物退出、对手第一胜、旧解法失效和地图切换等批次节点不能被局部细节挤掉。

若本章让人物跨地图继续同行，核对他是否“活得了、跟得上、有自己的事”；若引入主要对手，核对其是否能让旧解法失效并具备先赢一次的空间；若是回归配角，核对离开主角视野后的独立任务与至少两项状态变化。证据不足时不能靠临时血脉、点化或主角长期保护补洞。

单列“读感与自由发挥”：指出自由发挥在哪、是否成立、最吸引与最发闷的段落、节奏快慢。只要没有越红线，和规划者原先设想不同也应接受。

验收自由发挥时先问“后文是否必须记住”。不需要后文记账、只在本场闭合的细节，默认属于写手权限。不能用“工单没写”作为单独删除理由，也不能把有生命力的对话和动作改回规划者自己的分镜。

写手采用等效实现时，验收比较的是因果功能：作选择的人、代价、不可逆结果和后续接口一致，就应判为成立；场景顺序、动作载体或对话走法不同，不构成返工理由。

故事台账本身不是限制自由发挥的审批表。验收时只检查三件事：离开本场后是否需要记住、交接状态是否准确、是否越过短期边界。临时人物有自己的目标、筹码和退出点，且不改变主线硬结果，就应接受；不要因为规划者没预先取名而删除。

### 4. 机械验证

- 在 `F:\novel\百世飞升续写` 运行 `python 脚本/候选稿体检.py <候选稿> --min-chars <下限> --max-chars <上限> --scene-count-min <下限> --scene-count-max <上限> --scene-min <每场下限>`；只有要求逐字出现的原句和明确禁词才分别作为 `--require`、`--forbid`。不要沿用写手报告。
- 在同一目录运行 `python 脚本/文风体检.py <候选稿绝对路径>`。
- 人工搜索未登记专名、会改变连续性的剧情数字和脚本无法判断的同义改写；不要追杀自然量词与一次性现场细节。
- 候选稿未晋升 `分章/` 时，不用正式全本检查代替候选稿检查。

## 修复与返工边界

可以直接修复：术语、材质、称谓、局部动作顺序、清单式旁白、少量越线设定、章末落点和为恢复篇幅所需的局部场景补强。修后重跑字数、场长和文风。修改只触及有证据的问题，成立的现场细节保留。

需要退回：章节目标或不可逆结果缺失、关键人物选择相反、整场因果错误、必须新增未经裁定的设定才能补救，或局部修改会重写一整场以上。

不要因个人措辞偏好整章推倒；不要把已经成立的 20%—30% 自由发挥改成规划者自己的分镜。

## DevTrace 与收尾

通过时的 `test` 必须包含：

- 结论与实际修正
- 实测字数、场景长度和文风结果
- “读感与自由发挥”
- 本章不可逆结果
- 本章脉冲与仍欠的剧情债
- 下一章是否需要调整

item id 已知则 `review_work(pass/revise)`；旧内容已通过但队列仍显示 submitted 时，只有在 item id 明确的情况下补做正式 review。不要再次创建重复工单。

`review_work(pass)` 会把本工单待审故事卡原子转为下一位写手可见；`review_work(revise)` 会保留给原工单返修但不污染后续。若某张卡必须跨五章、跨卷或改变长期设定，先记录同项目 `decision` 并同步正式资料，再用 `story_review(promote, decision_event_id=...)`；不能只把临时卡改成长线。

每次验收只更新 `规划/当前批次索引.md` 中与当前批次有关的行；不要为了登记一章重写无关历史。长期口径变化另记 `decision`，连续性发现记 `finding`，未解决问题记 `risk`。

Git 提交不属于默认验收动作；只有用户已要求提交时，才按已闭环内容分批提交。
